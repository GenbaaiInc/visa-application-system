# 申請手続きと在留資格の整理（2026-09-13）

> 2026-09-14追記：下記は設計時点の整理。特定技能3手続きの実装を進めた結果と、検証済み・未検証の区別は[実装状況](実装状況.md)を参照。技人国の変更・更新は引き続き対象外。

更新1案件の入力候補・未入力項目と修正範囲は[2026-09-30のQAレポート](更新QA_入力項目と修正範囲_2026-09-30.md)を参照。

## 先に結論

利用者に見せる順番は、**①何の手続きか → ②対象となる在留資格**でよい。

```text
申請手続き
├─ 新規入国（認定・COE）
├─ 在留資格の変更
└─ 在留期間の更新
   それぞれで対象となる在留資格を選ぶ
   ├─ 技術・人文知識・国際業務（技人国）
   └─ 特定技能（1号／2号）
```

ここでの「新規」は**海外から日本へ入国するための認定申請**を意味する。単なる「新しい案件」ではない。COE（Certificate of Eligibility）は本来、在留資格認定証明書の略称。この文書では便宜上、その交付申請を「認定・COE」と呼ぶ。COEは在留資格の種類ではない。日本国内での「在留資格取得許可申請」はRASENS上でも別手続きなので、無限定の「新規」とは表示しない。[認定](https://www.moj.go.jp/isa/applications/procedures/16-1.html)・[変更](https://www.moj.go.jp/isa/applications/procedures/16-2.html)・[更新](https://www.moj.go.jp/isa/applications/procedures/16-3.html)は入管庁が別々の手続きとして案内している。

## ほぼ別々に作る、という方針

「技人国と特定技能に共通項目があるから、巨大な共通schema・画面・mappingを作る」は採らない。まず**手続き×在留資格ごとに、入力項目・AI抽出ルール・レビュー項目・RASENS変換を独立して設計**する。レビュー画面の骨格は共通のままでよい。異なる手続きを同じ `item[N]` で入力しない。

一方で、次の外枠だけは共通にする。

1. 案件の作成・一覧、資料のアップロード、権限、レビュー状態と証拠の表示、RASENSへの入力経路。
2. 案件を識別する `application_type`（手続き）、`target_status`（対象となる在留資格）、必要なら `target_status_variant`（特定技能1号／2号）。
3. 氏名・生年月日など、**意味が本当に同じ**既存の値。無理に全項目を共通化しない。案件ごとにその時点の情報を保持し、別案件や将来の人材管理システムから自動で上書きしない。

形としては、六つの「処理セット」を必要になった順に足す。先に六つの空実装を並べたり、全手続きの差を一つの条件式へ押し込んだりしない。

各処理セットには、その組合せ専用の「読む項目・人が見る項目・RASENSに入れる項目」をまとめる。`case_data` 全体を六回コピーする意味ではない。共通の氏名などは同じpathを使ってよいが、COE特有の入国予定、変更時の現在資格、更新時の在留期限、特定技能の支援情報を無理に同じ形へ押し込まない。**先に別々に明快に作り、同じ意味・同じ挙動だと確認できた部分だけ後から共通化する。**

| 手続き | 技人国 | 特定技能 |
|---|---|---|
| 新規入国（認定・COE） | 既存の処理が稼働 | 未入力RASENS画面を保存済み。抽出・変換は未実装 |
| 在留資格の変更 | 未実装。画面・資料を別途確認 | 未入力RASENS画面を保存済み。抽出・変換は未実装 |
| 在留期間の更新 | 未実装。画面・資料を別途確認 | 未入力RASENS画面を保存済み。抽出・変換は未実装 |

技人国の変更・更新も将来この二段階に加えられる。**変更では「現在の在留資格」と「変更後に希望する在留資格」を別に持つ**。更新も現に有する在留資格と更新対象を確認する。1号／2号、直接雇用／派遣、支援方法は、特定技能の当該手続き内で扱い、初日から別アプリや大量の処理セットへ分割しない。実画面で差が大きいと判明した箇所だけ、その時点で分ける。

2026-09-14の実画面確認では、2号へ切り替えても直前の1号の支援方法が残り、支援欄が入力可能な場合があった。また派遣先欄は、直接雇用かどうかにかかわらず画面上に存在した。**RASENSで入力可能な欄を全部埋める設計にはせず、案件の1号／2号・雇用形態・支援方法から、入力対象の行だけを作る。** 詳細は[実画面調査](RASENS調査.md)に記録した。

### 既存コードとの関係

既存案件の `case.application_type = certificate_of_eligibility` はそのまま維持する。これは「新規入国（認定・COE）」の内部値であり、値を `new` に改名する必要はない。変更は `change_of_status`、更新は既存UI定義にある `extension_of_stay` を使う。現在は技人国COEだけ処理可能で、未対応の組合せを技人国COEへ推測で流してはいけない。

UIはまず「手続き」→「対象となる在留資格」の二段階にし、対応していない組合せは選択できないか、選択後に未対応と明示する。案件の「新規作成」という操作と「新規入国」という手続きを同じ文言で呼ばない。

現行の案件作成UIとFrontend型はCOE固定なので、この二段階選択に合わせて変更が必要。backendのprofile解決は既にあるが、RASENS台帳・mappingの読込はまだ技人国COE固定なので、profileから該当ファイルを選ぶ処理も必要。

## データと検証をどう分けるか

各処理セットが持つのは、その手続きで**最終的にアプリが確認・保持すべき値**と、RASENSの物理入力先への対応である。PDFにある文字列、AI抽出結果、担当者が確認した値、RASENS入力行を同じものと扱わない。

```text
入力資料 → AI抽出候補 ＋ 根拠 → 人の確認後の案件データ
                                      → 手続き別のRASENS入力行 → 実画面
```

- 抽出精度: 資料から読める項目だけを、同じ処理セットのgolden（正解案件データ）と比較する。
- 変換精度: 正しい案件データから作った入力行を、期待するRASENS入力行と比較する。
- 実画面確認: 対象の手続き・在留資格・分岐が一致する画面で、表示／必須／入力先を確認する。
- 人の申告・確認事項は「資料になければ No」にはしない。未確認のまま自動入力しない。

まず**1案件（1人）ごと**に資料と確認済み正解値を照合し、案件単位で結果を確認する。変更と更新は別々の手続きとしてそれぞれ検証できるが、同じ人を「2人」とは数えない。後から案件が増えたときだけ、必要に応じて横断集計する。旧goldenや元資料は変更・上書きせず保存し、新しい処理セットに合うgoldenだけを別に作る。実資料と画面キャプチャはGit管理外のrestricted領域に置く。

## 実装順序（現時点の提案）

1. 画面調査で「手続き×在留資格」の実際の入口と分岐条件を台帳にする。静的MHTMLの全controlを実際の必須項目と見なさない。
2. UIを「手続き→在留資格」に整理し、未対応の組合せを安全に止める。既存技人国COEは維持する。
3. 最初の特定技能処理セットを一つだけ作り、資料→確認値→RASENS行→実画面を通しで検証する。どの手続き・分岐を最初にするかは画面調査の結果で決める。
4. 変更・更新と1号／2号・雇用形態・支援方法を、確認済みの組合せから追加する。技人国変更・更新は別の画面と入力資料を確認してから追加する。

将来の外国人従業員管理システムと連携する場合も、案件側はその申請時点のスナップショットを持つ。人材台帳と申請案件を同じデータベース・同じモデルに今から統合する必要はない。
