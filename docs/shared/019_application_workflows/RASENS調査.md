# RASENS実画面調査と残る確認（最終確認: 2026-09-14）

## 入口からの操作経路

毎回、利用者指定の[手続き一覧入口](https://www.rasens-immi.moj.go.jp/rasens-u/offer/offerList_initDisplay)から入り直す。途中の入力画面URLだけを開いても、手続き選択・同意・在留資格選択を再現できない。

1. 上記URLをChromeで開く。必要なら既存のログイン認証を使う。
2. 「オンライン申請手続き」を押す。
3. 手続き一覧で、次のいずれか一つを選ぶ。
   - 新規入国: 「在留資格認定証明書交付申請」
   - 変更: 「在留資格変更許可申請」
   - 更新: 「在留期間更新許可申請」
4. 画面上の注意事項を読み「同意する」を押す。
5. COE・変更では「希望する在留資格」、更新では「現在の在留資格」から「特定技能」を選び、「入力へ進む」で該当する入力画面へ進む。技人国調査では同じ位置で「技術・人文知識・国際業務」を選ぶ。
6. 画面上部で**選択中の手続き名・区分・在留資格**を確認してから、下記の分岐だけを調べる。

この調査では申請人の実情報を入力しない。**保存、申請実施、送信、確認画面での確定操作はしない。** 条件の切替だけでも副作用がありそうな操作は避ける。MHTML・スクリーンショットを追加保存するなら、個人情報がないことを確認し、Git管理外の `rasens-autofill/reference/` または `qa/screenshots/` に置く。

### 今回のライブ操作の到達点

2026-09-13にChromeで指定URLから新しいタブを開き、「オンライン申請手続き」を押すところまで操作した。そこで「利用者ログイン」へ遷移し、ログイン済み状態を新しいタブでは引き継げなかった。認証情報の取得も完了せず、**この入口から手続き一覧・同意・入力Sまで通しで再実行する調査は未完了**。一方、以前から開いていたRASENS申込タブでは「在留資格変更許可申請（区分V）」と「希望する在留資格：特定技能」を読み取り確認した。既存タブの内容確認は、今回の入口からの再現成功とは数えない。

このため、以下の操作経路は過去の保存画面・これまでの操作に基づく再確認手順であり、今回の新規タブで全段階を実測した結果ではない。ログインが利用できる状態になったら、まずこの入口から再開する。

### 2026-09-14の共有Chrome再試行

指定URLから新しいRASENSログイン画面までは到達した。ChromeのBitwarden候補を使うと利用者IDだけが入力され、パスワード欄は埋まらなかった。古いログインタブでの再試行はRASENSの「セキュリティエラー／不正な画面操作」となったため、以後は新しいログイン画面だけを使い、認証を突破する操作は続けていない。**利用者が共有Chromeの新しいログイン画面でログインを完了した後に、入口から3手続きを再調査する。**

既存のログイン済み「変更×特定技能」フォームは読み取りのみで確認した。画面には希望する在留資格の「特定技能１号／２号」、支援方法の「登録支援機関に委託する／委託しない」、派遣先欄があり、2号では支援委託項目の入力が不要との案内がある。委託側には登録支援機関の基本情報・登録番号・支援担当者等、委託しない側には自社の支援責任者・担当者等の項目がある。ただし**選択肢を切り替えた時の表示／必須状態は未測定**であり、COE・更新へ新規ログイン経由で到達した結果でもない。既存フォームから「手続き検索」へ戻ると入力中データ破棄の警告が出るため、遷移しなかった。

### 2026-09-14、利用者ログイン後の実画面確認

共有Chromeで指定URLから入り直し、「オンライン申請手続き」→手続き一覧→各手続き→「同意する」→「特定技能」→「入力へ進む」で、COE・変更・更新それぞれの未入力画面まで到達した。個人情報は入力せず、保存・申請実施・送信はしていない。前記のログインできなかった記録は過去の経緯であり、**入口から3手続きへ進めない問題は解消した**。

|---|---|---|
| COE | `11 入国目的` | 1号では支援計画 `4.1〜4.16` が画面上に現れ、2号ではその項目群が画面上から外れる |
| 変更 | `13.1 希望する在留資格` | 1号／2号で支援計画 `4.x` の表示が変わる |

COEの1号画面では、支援方法を「委託する」にすると登録支援機関名 `5.1` は表示・入力可能、自社支援責任者名 `3.44` は非表示・入力不可になった。「委託しない」では逆になった。**項目はDOMから削除されるのではなく、画面上の表示と入力可否が切り替わる**。選択前には両方とも表示・入力可能だった。したがって、DOM上の存在や `disabled` の状態だけで、入力すべき項目を判定しない。

2号は画面文言上、支援委託の入力が不要。ただしCOE画面で1号・「委託しない」を選んでから2号へ切り替えると、直前の選択が残り、`3.44` が入力可能のままだった。**2号で自社支援情報を自動入力すべき、という意味ではない**。案件側の1号／2号条件を優先して生成対象を決める必要がある。

派遣先欄 `2.21〜2.29` は3手続きのHTMLにあり、COEの未入力画面では入国目的や支援方法の選択前から画面上に表示され入力可能だった。説明文は「労働者派遣の対象とする場合に入力」。大きな「直接雇用／派遣」スイッチはこの調査で確認できていない。**派遣欄が入力可能だからといって、直接雇用案件で値を埋めない**。

ここまで確認したのは表示・入力可否・選択肢であり、**実際の必須チェック／エラー条件は未検証**。検証のために申請人情報を入れたり保存・送信したりはしていない。

### 2026-09-14、必須エラー・派遣条件の再調査

指定入口からChromeの新規タブで「オンライン申請手続き」を押すと、利用者ログイン画面へ遷移した。既存の手続き一覧タブでも、指定入口から入り直すと同じログイン画面へ遷移した。**この時点では認証が切れており、今回の実画面での空欄エラー確認と派遣条件の動的確認は未実施**。前節のログイン後実画面確認まで取り消す意味ではなく、再調査時の状態を記録している。認証情報の入力、個人情報の入力、保存・申請は行っていない。

保存済みのCOE・変更・更新のMHTMLを照合すると、3画面とも入力欄にHTMLの `required` / `aria-required` 属性がなく、画面の「必須」印は多数ある。印のある要素には非表示・条件付きのものも含まれるため、**属性や印の数から実際の必須条件を決められない**。派遣先 `2.21〜2.29` に静的な「必須」印はない。MHTMLには動作を決めるJavaScriptが保存されていない。「確認へ進む」はフォームのPOST送信ボタンであり、その先で保存等が起こるか静的資料から判断できないため押していない。

派遣に関する画面ラベル・注意書きは3手続きで同じだった。

| 項目群 | 保存済み画面で読めた意味 | 確認の限界 |
|---|---|---|
| `2.21〜2.29` 特定技能雇用契約(12)派遣先 | 派遣先の名称、法人番号の有無・番号、雇用保険適用事業所番号、郵便番号・住所、電話、代表者、派遣期間の始期・終期。「労働者派遣の対象とする場合に入力」 | どの資料のどの値を採るか、動的必須条件は未確認 |
| `3.1〜` 特定技能所属機関、`3.15〜` 勤務させる事業所 | 派遣先欄とは別に所属機関と実際の勤務先に関する欄がある | 同じ会社・所在地となる場合を含め、案件資料との対応は未確認 |
| `3.37〜3.39` 派遣時の該当事項 | 3.37は一定の事項に該当するかの有無、3.38は該当事項と詳細、3.39は派遣先が所定の要件に該当するかの有無・詳細。いずれも派遣対象の場合の案内がある | 3.37の選択で3.38の入力が変わるとの文言はあるが、実画面切替・必須エラーは未確認 |

「直接雇用／派遣」を一括して切り替える選択肢は、保存済み3画面からは見つかっていない。派遣の適用条件は画面の注意書きに基づき、人が資料を確認して判断する必要がある。**派遣先欄と所属機関欄を同一会社として自動コピーしない。**

## 特定技能で調べる分岐

以下は「必要な確認シナリオ」。**1号／2号と支援方法の画面切替は確認済みだが、必須チェックと実データを用いた入力結果は未検証**。一度に全組合せを掛け算せず、まず差が出る四つに絞る。

| シナリオ | 操作して確認すること | 記録する結果 |
|---|---|---|
| 1号・直接雇用・登録支援機関へ委託 | 1号と「委託する」を選ぶ。派遣欄は説明文に従って空欄にする | 登録支援機関欄の表示・入力可否は確認済み。必須は未検証 |
| 1号・直接雇用・自社支援 | 「委託しない」へ切り替える | 自社支援欄の表示・入力可否は確認済み。必須は未検証 |
| 1号・派遣 | 派遣対象資料を確認する。画面に明確な派遣切替は見つかっていない | 派遣先・契約・受入機関欄の適用条件と必須は未検証 |
| 2号 | 1号から2号へ切り替える | 支援計画欄の非表示などは確認済み。前の支援方法の選択が残る場合あり。必須は未検証 |

各シナリオをまずCOEで確認し、同じ四シナリオを変更・更新に機械的に当てはめず、当該手続きにその選択肢があるかから確認する。選択肢がない、または本人情報を入れないと遷移できない場合は「未確認」と記録する。制度上「2号は支援不要」などの知識だけで、実画面の必須属性を決めない。

1項目の記録は、**手続き／在留資格／分岐、画面ラベル、表示有無、必須有無、DOM識別子、根拠画面、確認日**だけでよい。画面全controlを最初から台帳化しない。最初に分岐と自動入力対象の項目を確認し、必要分だけ増やす。

## 実装前に何が必要か

- 3手続きの1号／2号・支援方法・派遣欄の表示と入力可否、および可視の「必須」印は確認済み。残るサーバー側の空欄エラーは、「確認へ進む」の副作用が分からない間は操作せず未確認とする。実際に自動入力する項目のラベル・入力先も個別に照合し、PIIを含まない証拠だけを追加する。
- 技人国の変更・更新を追加する前には、それぞれの最新実画面を別途確認する。COE技人国のmappingを流用しない。
- AI抽出の精度は、まず1案件（1人）ごとに入力資料と確認済み正解値で測る。変更・更新が同じ人なら別手続きとしてそれぞれ検証できるが、人物数は二人と数えない。
- `input/`（AIへ渡す元資料）、`expected_verified/`（人が確認した案件正解値）、必要なら `output/`（RASENS結果）を混ぜない。人が申告すべき項目は抽出精度の分母から外し、人確認後にだけ入力へ進める。

画面確認が終わるまでは「実装の外枠は作れるが、全分岐の正しい自動入力は保証できない」と扱う。
